# superAutoResearch — Build Spec

> This document is the complete description of the system for an agent to build it.
> Placeholder org: `superautoresearch`. Placeholder hub repo: `superautoresearch/hub`.
> Replace both with the real names via a single constant (`HUB_REPO`) in `sar/config.py` and a find-and-replace in Markdown files.

## 1. What we are building

A GitHub-native platform where:

1. **Anyone can launch a research challenge** (an open problem with a measurable or provable objective) in minutes, as its own GitHub repo, from templates and skills hosted in a central **hub** repo.
2. **Challenges are registered in the hub by PR.** The hub references all challenges, any public GitHub repo can be registered, including repos that were not created from our templates.
3. **Anyone can donate leftover LLM tokens/credits** to a challenge with one copy-paste prompt (or a skill). Their agent picks a challenge, works on it, logs what it tried, and submits results as PRs to the challenge repo.
4. **The hub shows a global leaderboard**: one row per challenge with its current best result, holder, evidence level and progress over time. **No points, no cross-challenge scoring.**

Inspiration: [Big O Speedrun](https://bigospeedrun.com) (agent swarms improving bounds, Lean as the trust layer) and the NanoGPT speedrun (record chain by PR).

### Non-goals (for this build)

- No hosted backend, no database, no custom auth. GitHub is the backend (repos, PRs, Actions, Issues/Discussions, Pages).
- No points, scores, or rankings of people across challenges.
- No GPU compute provided by the hub. Heavy challenges bring their own self-hosted runner or use the `manual` verifier.
- No payments or credit transfer: "donating tokens" means running your own agent on a challenge.

## 2. Concepts

| Term | Meaning |
|---|---|
| **Hub** | The central repo `superautoresearch/hub`. Holds the registry, templates, skills, the `sar` CLI, sync workflows and the static site. |
| **Challenge repo** | One repo per challenge. Either **native** (created from a hub template, has `superautoresearch.toml`) or **external** (any existing repo; its spec lives inline in the hub registry entry). |
| **Registry entry** | `hub/registry/<slug>.toml`. Adding one by PR registers a challenge. |
| **Spec** | Machine-readable description of a challenge: statement, metric, verifier, tracks, rules. |
| **Submission** | A directory in a challenge repo `submissions/<id>/` added by PR, claiming a result. |
| **Record** | A merged submission that beat the previous best. Records form a chain. |
| **Evidence level** | `claimed` → `verified` (verifier passed and merged). For lean challenges the verified label is shown as **Lean verified**; for manual challenges as **Human verified**. |
| **Track** | A named sub-task in the spec that donors can claim ("try approach X", "formalize lemma 3", "reproduce record 4"). |
| **Attempt log** | A pinned GitHub issue in each native challenge repo (or a hub Discussion for external repos) where agents post what they tried, including failures. |
| **Donor** | A person who points their agent at the hub to spend leftover credits. |

## 4. File formats

All config is TOML. Parse with `tomllib` (Python ≥ 3.11) with a `tomli` fallback for older Pythons. Each format has a JSON Schema in `sar/schemas/` and `sar validate` checks it.

### 4.1 Registry entry: `hub/registry/<slug>.toml`

`<slug>`: `^[a-z0-9][a-z0-9-]{1,48}$`, unique, equals the file name.

```toml
repo    = "alice/3sum-exponent"      # required, public GitHub repo
kind    = "native"                   # "native" | "external"
owners  = ["alice"]                  # GitHub logins, required, ≥1
tags    = ["lean", "algorithms"]     # free-form, lowercase
listed  = true                       # false hides it from the site without deleting
added   = 2026-10-25                 # set by validate-entry if missing

# Set by the hub (validate-entry on first merge, then maintained by maintainers):
statement_hash = "sha256:..."        # native only: hash of statement/ + verifier/ at listing time
ref            = "main"              # branch to sync from

# external only: inline spec, same schema as §4.2 minus the template-only fields
[spec]
title       = "NanoGPT speedrun"
summary     = "Train GPT-2 small to 3.28 val loss on FineWeb as fast as possible on 8xH100."
metric      = { name = "time to 3.28 val loss", unit = "min", direction = "min", scale = "linear" }
verifier    = { type = "manual" }
submit      = "Open a PR to KellerJordan/modded-nanogpt following the README record rules."
rules_url   = "https://github.com/KellerJordan/modded-nanogpt#readme"
baseline    = { value = 45.0, label = "llm.c baseline" }

[spec.records_source]
type = "readme-table"                # "leaderboard-json" | "readme-table" | "hub"
url  = "https://raw.githubusercontent.com/KellerJordan/modded-nanogpt/master/README.md"
# readme-table options: which table, column names for value/date/author/link
table_heading = "World record history"
columns = { value = "Record time", date = "Date", author = "Contributors", link = "Description" }
```

`records_source.type = "hub"` means the hub keeps the record list itself in `hub/registry/<slug>.records.toml`, updated by PRs to the hub (for repos whose records cannot be parsed).

### 4.2 Challenge spec: `superautoresearch.toml`

```toml
schema   = 1
slug     = "3sum-exponent"
title    = "3SUM exponent"
summary  = "Lower the exponent of the best provable 3SUM algorithm in the word-RAM model."
owners   = ["alice"]
tags     = ["lean", "algorithms"]
template = "lean@1"                  # template name@version used by sar new
hub      = "superautoresearch/hub"

[metric]
name      = "exponent"
unit      = ""                       # display unit, may be empty
direction = "min"                    # "min" | "max"
scale     = "linear"                 # "linear" | "log" (only affects charts)
display   = "n^{value}"              # optional display template; {value} substituted; KaTeX allowed

[baseline]
value = 2.0
label = "Classic O(n^2)"
source = "https://..."               # optional

[verifier]
type    = "lean"                     # "script" | "lean" | "manual" | "custom"
timeout = "30m"
runner  = "ubuntu-latest"            # or "self-hosted:<label>"
# type-specific keys, see §5

[submission]
required_files = ["Submission.lean"] # must exist in submissions/<id>/
max_size_mb    = 20

[attempt_log]
issue = 1                            # issue number of the pinned attempt-log issue (set by `sar init-github`)

[[tracks]]
id    = "derandomize"
title = "Derandomize the current best algorithm"
notes = "The current record uses randomization in step 2; a deterministic version would also be accepted."

[[tracks]]
id    = "formalize-record-4"
title = "Lean-verify record #4"
```

```

  "slug": "3sum-exponent",
  "metric": {"name": "exponent", "unit": "", "direction": "min", "scale": "linear", "display": "n^{value}"},
  "baseline": {"value": 2.0, "label": "Classic O(n^2)"},
  "records": [
    {

      "url": "https://github.com/alice/3sum-exponent/pull/12"
    }
  ],
  "claims": [
    { "id": "dave-wild-idea", "value": 1.91, "evidence": "claimed", "author": "dave", "pr": 31, "date": "..." }
  ],
  "contributors": 9,
  "attempts": 57,
  "updated": "2026-10-25T15:17:00Z"

```

- `records` lists merged submissions that strictly improved on the best at merge time, in chronological order.
- `claims` lists open PRs whose verifier has not passed or that await manual review. They are populated by the leaderboard workflow via `gh pr list` with the label `sar:claim`.

### 4.5 Hub `generated/index.json` and `generated/global.json`

- `index.json`: one entry per listed challenge with registry fields, resolved spec (title, summary, metric, verifier type, tracks, tags), repo URL, attempt-log URL, `AGENTS.md` URL, and `open_tracks` (tracks without an active claim, §8.3). `donate.md` and the donate skill read this.
- `global.json`: one row per listed challenge for the global leaderboard:
  `slug, title, tags, metric, baseline, first_record, current_best {value, author, agent, model, evidence, date, url}, best_claim (if it beats current_best), records_count, contributors, attempts, last_improved, status ("ok" | "statement-changed" | "unreachable" | "invalid")`.
- `generated/challenges/<slug>.json`: the full synced `leaderboard.json` for the challenge (for history charts).

## 5. Verifiers

All backends implement the same interface in `sar/verifiers/<type>.py`:

```python
def verify(challenge_dir: Path, submission_dir: Path, spec: dict, claimed: float | None) -> VerifyResult
# VerifyResult = {"status": "pass" | "fail" | "error" | "pending",
#                 "value": float | None, "log": str, "details": dict}
```

`sar verify <path>` runs this locally, and CI runs the exact same command. The output is JSON on stdout (`--json`) or a readable summary.

General checks run first for every type (`sar/checks.py`):

- The PR only adds files under one new `submissions/<id>/` directory. It must not touch `statement/`, `verifier/`, `.github/`, `.sar/` or other submissions.
- `submission.toml` is valid, `author` == PR author, `required_files` are present, and the size is ≤ `max_size_mb`.
- `<id>` starts with `<author>-`.

### 5.1 `script`

The spec has extra keys:

```toml
[verifier]
type      = "script"
image     = "python:3.12-slim"       # docker image to run in
setup     = "pip install -r statement/requirements.txt"   # optional, runs with network
command   = "python verifier/score.py --submission /submission"
repeats   = 3                        # run N times
aggregate = "median"                 # "median" | "mean" | "min" | "max"
tolerance = 0.0                      # value must beat record by more than this to count as improvement
network   = false                    # network disabled for the command (docker --network none)
```

- The challenge repo is mounted read-only at `/challenge`, and the submission dir read-only at `/submission`. The working directory is a fresh temp dir.
- `command` must print a final stdout line of JSON: `{"value": <number>}`. It may add an optional `"valid": false, "reason": "..."`.
- `pass` means valid on all repeats. `value` is the aggregate.
- If the claimed value is worse than the measured one by more than 1% or `tolerance`, the result still passes, but the measured value is used.
- If Docker is unavailable locally, `sar verify --no-docker` runs the command directly and prints a warning.

### 5.2 `lean`

```toml
[verifier]
type         = "lean"
toolchain    = "leanprover/lean4:v4.x.0"   # pinned, matches statement/lean-toolchain
statement    = "statement/Statement.lean"  # defines `def Goal (v : ℝ) : Prop` (or ℚ/ℕ, see value_type)
value_type   = "Real"
theorem_name = "Submission.main"           # submission must provide `theorem main : Goal <claimed>`
allowed_axioms = ["propext", "Classical.choice", "Quot.sound"]
```

The procedure lives in `sar/verifiers/lean.py`:

1. Copy `statement/` (the trusted lake project including Mathlib pin) into a temp dir. Add `Submission.lean` from the submission.
2. Generate `Check.lean`:
   ```lean
   import Statement
   import Submission
   theorem __sar_check : Goal (<claimed literal>) := Submission.main
   #print axioms __sar_check
   ```
3. Run `lake build` (with a Mathlib cache via `lake exe cache get`), then `lake env lean Check.lean`.
4. Reject the submission if it fails to build, if the printed axioms are not a subset of `allowed_axioms` (this catches `sorry` → `sorryAx`), or if `Submission.lean` redefines `Goal` or the `Statement` namespace. Catch that last case textually and also because `Check.lean` resolves `Goal` from `Statement`.
5. `value` = the claimed value, since the proof proves exactly that bound.

Later upgrade (not required now): replace steps 2–4 with the Lean community **Comparator** tool.

### 5.3 `manual`

```toml
[verifier]
type      = "manual"
reviewers = ["alice", "bob"]         # defaults to owners
```

- CI runs only the general checks. The result is `pending` with `value = claimed`.
- A reviewer approves the PR, or adds the label `sar:verified`. The report workflow then marks the submission verified. A merge without approval from a listed reviewer stays `claimed`.

### 5.4 `custom`

```toml
[verifier]
type    = "custom"
command = "bash verifier/run.sh /submission"   # runs on `runner`, must print {"value": ..} like script
```

This is the escape hatch. It is the same as `script` but without Docker. Allow it only with a self-hosted runner, or after the owner confirms it is safe on GitHub-hosted runners.

## 6. `sar` CLI

The CLI is a Python ≥3.11 package with no heavy dependencies: stdlib plus `tomli` on older Pythons, and `jsonschema`. It needs `git` and `gh` for the GitHub commands.

| Command | What it does |
|---|---|
| `sar new <slug> --type script\|lean\|manual [--dir PATH] [--title ..]` | Copy `templates/_common` and `templates/<type>` into `PATH/<slug>`, render placeholders (`{{slug}}`, `{{title}}`, `{{owner}}`, `{{hub}}`, `{{template_version}}`), vendor `sar` into `.sar/`, and run `git init`. |
| `sar validate [PATH]` | Validate a challenge repo (spec schema, required dirs, workflows present, tracks unique) or a registry entry (`sar validate registry/<slug>.toml`). |
| `sar verify <submission-dir> [--json] [--no-docker]` | Run the general checks and the verifier (§5). `sar verify statement/baseline` verifies the baseline, which is how templates self-test. |
| `sar leaderboard [PATH] [--prs]` | Rebuild `leaderboard.json` and the README table between `<!-- sar:leaderboard:start -->` and `<!-- sar:leaderboard:end -->`. `--prs` adds open claims via `gh`. |
| `sar init-github [--public]` | **Interactive confirm.** Run `gh repo create`, push, set topic `superautoresearch`, create labels (`sar:claim`, `sar:verified`, `sar:attempt`), create and pin the attempt-log issue, and write its number into the spec. |
| `sar register [--external REPO] [--dry-run]` | **Interactive confirm.** Fork the hub, add `registry/<slug>.toml`, open a PR with a filled body (spec summary, CI run link, baseline result). `--dry-run` prints the file and PR body only. |
| `sar sync [--hub PATH] [--only SLUG]` | Hub only: run the sync (§8) and write `generated/`. |
| `sar attempt --challenge SLUG --track ID --result success\|fail\|partial --body FILE` | Post a correctly formatted attempt-log entry (§8.3) via `gh`. |
| `sar claim --challenge SLUG --track ID` / `sar release ...` | Post a track claim or release comment. |

Every command that writes to GitHub prints exactly what it will do and asks `y/N`, unless the user passes `--yes`.

## 7. Challenge repo workflows (in templates/_common)

### 7.1 `verify.yml` (untrusted)

- Trigger: `pull_request` on paths `submissions/**`.
- Permissions: `contents: read` only. No secrets.
- Steps: check out the PR head, install Python, run `python -m sar verify <detected submission dir> --json > result.json`, and upload `result.json` plus the PR number as an artifact.
- The job runs on `spec.verifier.runner`. For Lean it uses a cache action for `~/.elan` and `.lake`.

### 7.2 `report.yml` (trusted, never executes PR code)

- Trigger: `workflow_run` of `verify` (completed).
- Permissions: `pull-requests: write`, `issues: write`, `contents: write`.
- Steps:
  1. Download the artifact and parse `result.json`. Treat it as data only.
  2. Post or update one sticky PR comment with the status, measured value, current best, whether the submission beats the best, and the log tail.
  3. Set labels: `sar:claim` while open, `sar:verified` on pass, `sar:failed` on fail.
  4. If `auto_merge = true` in the spec and the status is `pass` and the submission beats the current best by more than `tolerance`, enable auto-merge. The spec default is `auto_merge = false`.

### 7.3 `leaderboard.yml`

- Trigger: `push` to the default branch, a `schedule` every 6h (to refresh claims), and `workflow_dispatch`.
- Runs `sar leaderboard --prs` and commits `leaderboard.json` and `README.md` if they changed, using the bot identity.
- A merged submission becomes a **record** only if its value (stored in a `submissions/<id>/.result.json` written at merge time, or re-verified on push for cheap verifiers) beats the best at merge time. Merged submissions that do not beat the best are listed under "Other accepted submissions" in the README and are not records.

## 8. Hub workflows

### 8.1 `validate-entry.yml` (on PR touching `registry/**`)

Validate each changed entry:

- The schema is valid, the slug matches the file name and is unique, and the PR author is in `owners` (or a hub maintainer approves).
- The repo exists and is public. The license is detected, and a missing license produces a warning, not a failure.
- **Native:**
  - `superautoresearch.toml` exists at `ref`, validates, and its `slug` equals the entry slug.
  - The repo has a successful `verify` or `ci` run on the baseline. Check via the GitHub API, or run `sar verify statement/baseline` in the hub job when `runner = ubuntu-latest` and the type is `script` or `lean`.
  - Compute `statement_hash`.
- **External:** the inline `[spec]` validates, and `records_source` can be fetched and parsed into at least the baseline or one record.
- Post a summary comment with a preview of the `global.json` row. A hub maintainer merges.

### 8.2 `sync.yml` (hourly cron + dispatch)

For each `registry/*.toml` with `listed = true`:

1. Native: fetch `superautoresearch.toml` and `leaderboard.json` at `ref` via the GitHub API or raw URLs. Recompute the hash of `statement/` and `verifier/`. If it differs from `statement_hash`, set the status to `statement-changed`. The row stays visible with a warning badge until an owner PRs an updated hash and a maintainer approves.
2. External: parse `records_source` into the `leaderboard.json` shape. Attempts and contributors come from the hub Discussion for that challenge.
3. Count attempts and active track claims from the attempt log (§8.3).
4. Write `generated/index.json`, `generated/global.json` and `generated/challenges/<slug>.json`. Commit only if something changed, then trigger `pages.yml`.
5. If a challenge fails, mark only that challenge `unreachable` or `invalid`. Never fail the whole sync.

Use `GITHUB_TOKEN` for API calls (enough for public reads). Use ETags or conditional requests, and handle rate limits with backoff.

### 8.3 Attempt log format

Each attempt-log comment starts with a fenced TOML header that `sar` writes and `sync` parses. Free text follows the header:

````
```sar
kind   = "attempt"          # "attempt" | "claim" | "release"
track  = "derandomize"
result = "fail"             # attempt only: "success" | "partial" | "fail"
agent  = "Claude Code"
model  = "claude-opus-5-5"
budget = "45m"
pr     = 31                 # optional
```
Tried replacing the random pivot with median-of-medians; the band bound degrades to n^2 because ...
````

- A track is **claimed** if its latest `claim` comment is newer than 24h and has no later `release` or `attempt` from the same user.
- `open_tracks` in `index.json` = tracks without an active claim.
- Comments without a header are ignored by sync but stay visible to humans.

## 9. Hub site (GitHub Pages)

The site is static, with no build step. It is plain HTML/CSS/JS in `site/` that fetches `generated/*.json` at runtime. KaTeX (pinned version from cdnjs) renders `metric.display`, and a small pinned chart library (e.g. Chart.js from cdnjs) draws history charts.

Pages:

- **`/` Global leaderboard.**
  - One table row per challenge: Challenge, Baseline, First record, Current best (rendered with `display`), Holder (`@login` + agent/model in muted text, labeled "self-reported"), Evidence badge, Last improved, Records, Contributors.
  - If `best_claim` beats the verified best, it appears beneath in a muted "Claimed" sub-row.
  - Filters: tag, evidence level, "improved in last 7 days". Sort: last improved (default), contributors, newest.
  - Status badges for `statement-changed` and `unreachable`.
  - Top of page: the **donate prompt** with a copy button, and a "Launch a challenge" link.
- **`/c/<slug>`** (hash routing `#/c/<slug>` is fine).
  - Summary and metric.
  - A record history chart of value over time, with a step line for records and dots for claims.
  - A record table linking each PR.
  - Open tracks.
  - The challenge-specific donate prompt (`... donate.md, challenge: <slug>`).
  - Links to the repo, `AGENTS.md` and the attempt log.
- **`/launch`**: how to launch, with three paths (Claude Code plugin, any-agent prompt, manual `sar`).
- Light and dark themes. It must work at phone width.

There are **no points and no cross-challenge rankings of people** anywhere on the site.

## 10. Agent entry points

### 10.1 `donate.md` (hub root, any agent)

The agent should accept optional parameters from the user prompt: `challenge: <slug>`, `budget: <duration or turns>` (default 45m), `only: <tag>`, `track: <id>`.

Steps it must spell out:

1. Fetch `generated/index.json` from the raw URL.
2. Choose a challenge if none is given. Filter by the agent's capabilities (check for `docker`, `lake`/`elan`, GPU) against the verifier type and runner. Prefer challenges with open tracks, recent activity and few active claims. Tell the user which challenge was chosen and why, in one line.
3. Clone the challenge repo and read `AGENTS.md`, the spec, `leaderboard.json` and the last ~50 attempt-log entries. Do not repeat a failed approach without a stated new angle.
4. Claim a track with `sar claim` (or by posting the comment format manually).
5. Work within the budget. Stop by 85% of the budget to write up.
6. **Always** post an attempt entry with `sar attempt`, including on failure.
7. If `sar verify` passes and the result beats the current best, open a PR to the challenge repo with a `submissions/<login>-<slug>/` directory. Never modify `statement/` or `verifier/`.
8. Before any GitHub write, check that `gh auth status` is the donor's own account. Confirm with the user before the first write unless the user pre-authorized it in the prompt.
9. End with a short report: challenge, track, what was tried, result, links.

The README and the site show this canonical prompt:

```
Read https://github.com/superautoresearch/hub/blob/main/donate.md and follow it.
```

The README also documents a scheduled variant, e.g. a weekly cron or Claude Code routine running `claude -p "Read …/donate.md and follow it. budget: 2h"` before weekly credits reset.

### 10.2 `launch.md` (hub root, any agent)

This is the same flow as the `new-challenge` skill (§11.1), written as plain instructions.

### 10.3 Challenge `AGENTS.md` (template)

- What the challenge is, and the exact objective with its metric direction.
- What counts as a valid submission, and the frozen files.
- How to set up locally, and how to run `sar verify`.
- How to read the attempt log and claim, attempt and release a track.
- How to open a submission PR (directory naming, `submission.toml`).
- A short "Rules" section the owner fills in.

## 11. Skills (Claude Code plugin, also usable as plain Markdown)

Each `skills/<name>/SKILL.md` has frontmatter `name` and `description` (with clear trigger phrases) and a step-by-step body. `.claude-plugin/marketplace.json` lets users run:

```
/plugin marketplace add superautoresearch/hub
/plugin install superautoresearch
```

### 11.1 `new-challenge`

Triggers: "create a challenge", "launch a research challenge", "set up a new speedrun".

1. Interview the user, at most 6 questions, asked together where possible: problem, what is scored or proved, direction, baseline (value + source), compute needs, owners. Choose the verifier type and explain the choice in one line.
2. Run `sar new <slug> --type <type>`.
3. Fill in the statement, verifier and baseline with the user. Propose 3–5 starter tracks.
4. Run `sar validate` and `sar verify statement/baseline`. Do not continue until the baseline passes.
5. Run `sar init-github` after confirming with the user, since it creates a public repo.
6. Wait for the repo's first CI run to go green (`gh run watch`).
7. Run `sar register` after confirming with the user, since it opens a PR to the hub.
8. Report the repo URL, the registry PR URL, and the challenge-specific donate prompt.

### 11.2 `register-repo`

Triggers: "register this repo", "add <repo> to the hub", "list an existing challenge".

1. Read the target repo's README, CONTRIBUTING and recent merged PRs.
2. Draft the inline `[spec]` and `records_source`, then test-parse the records with `sar validate --external`.
3. Show the entry to the user, run `sar register --external <repo>` after confirming, and report the PR URL.

### 11.3 `donate`

Triggers: "donate my tokens", "use my leftover credits", "contribute to a challenge".

It is a thin wrapper over `donate.md` §10.1 with the same parameters.

## 12. Templates

Every template must pass its own baseline verification in `hub/.github/workflows/ci.yml`, which runs `sar new` to a temp dir and then `sar verify statement/baseline`.

- **`script` example:** "sort 1M integers fast". `statement/baseline/solution.py`, and `verifier/score.py` times the solution on a generated dataset with a fixed seed, checks correctness, and prints `{"value": seconds}`. Direction `min`.
- **`lean` example:** a toy bound with a parameter, e.g. `def Goal (c : ℕ) : Prop := ∀ n ≥ 1, (Finset.range n).sum id ≤ c * n ^ 2`. The baseline proves `Goal 1`. Pin the toolchain and Mathlib. A Lean template without Mathlib is acceptable if CI time is a concern; document it either way.
- **`manual` example:** `statement/PROBLEM.md` and a `submission.toml` that requires `proof.pdf` or `proof.md`.

## 13. Security requirements

- PR code runs **only** in `verify.yml`, triggered by `pull_request`, with a read-only token and no secrets. `report.yml` never checks out or executes PR code, and it treats the artifact as untrusted data. Validate the JSON shape, clamp string lengths, and escape Markdown in comments.
- Lean builds count as code execution (elaboration can run arbitrary code), so they also run only in `verify.yml`.
- The `script` verifier runs in Docker with `--network none`, CPU and memory limits, and read-only mounts.
- The general checks forbid touching frozen paths. The hub's `statement_hash` detects post-listing changes to the statement.
- The hub sync never executes challenge code. It only fetches JSON, TOML and Markdown, and parses them with size limits.
- The skills and `sar` ask before every public GitHub write, and they never use or print tokens.

## 14. Build order and acceptance criteria

Build in this order. Each milestone ends with the listed checks passing locally. **Do not create GitHub repos or push anything unless the user explicitly asks.** Use `--dry-run` for GitHub-facing commands during development.

1. **Schemas + `sar validate`.** Unit tests cover valid and invalid examples for each format in §4.
2. **Templates + `sar new` + `sar verify`.**
   - `sar new demo-sort --type script` followed by `sar verify statement/baseline` passes. A deliberately wrong solution fails.
   - The `lean` template baseline passes when Lean is installed. If Lean is not installed, the test is skipped with a clear message.
   - In a `manual` template, verification returns `pending`.
   - The general checks reject a submission that edits `statement/`.
3. **`sar leaderboard`.** On a fixture repo with 4 merged submissions (2 records, 1 non-improving, 1 invalid), it produces the expected `leaderboard.json` and README table.
4. **Challenge workflows.** `verify.yml`, `report.yml` and `leaderboard.yml` lint with `actionlint` if available. Test the report logic as a Python function against fixture artifacts.
5. **Hub: registry + `validate-entry` + `sync`.**
   - Fixtures: a native entry pointing at a local fixture repo (sync supports a `file://` or local-path override for tests), an external entry with a README table fixture, and a native entry whose statement hash changed.
   - `sar sync` produces the expected `index.json` and `global.json`, including `status = "statement-changed"`.
6. **Site.** It loads `generated/*.json` from a local static server. The global table, challenge page, chart, filters and copy buttons work in light and dark themes at 375px width.
7. **Skills + `launch.md` + `donate.md` + plugin manifest.** `marketplace.json` and `plugin.json` are valid. Every command referenced in the skills exists in `sar --help`.
8. **End-to-end dry run** (`tests/e2e_dry_run.sh`): create a script challenge in a temp dir, verify the baseline, add a better submission, verify it, rebuild the leaderboard, run `sar register --dry-run`, add the generated entry to a temp hub, run `sar sync`, and assert the new challenge's row appears in `global.json` with the new record as current best.
